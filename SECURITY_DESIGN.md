# SecureVault — Security Architecture & Threat Model Design (SECURITY_DESIGN.md)

## 1. Threat Model

SecureVault is designed as a **mobile-first, zero-knowledge, local-first client-side credential vault**. 
All cryptographic transformations occur strictly inside the browser environment utilizing the native W3C Web Cryptography API (`crypto.subtle`). 

### Threat Actors & Attack Vectors:
* **Local Storage / Persistence Inspection:** Adversaries gaining physical access to the device or local filesystem (inspecting IndexedDB, raw browser SQLite databases, or exported backups).
* **Cross-Site Scripting (XSS) / Extension Script Injections:** Malicious scripts running in the page context attempting to read decrypted credentials from memory or intercept unencrypted inputs.
* **Shoulder Surfing / Casual Observation:** Observers in physical proximity viewing passwords, CVVs, or card numbers over the user's shoulder.
* **Clipboard Sniffing:** Background clipboard monitors or malicious applications reading sensitive credentials after copy operations.
* **Dormant / Abandoned Session Exploitation:** Unattended device left unlocked after user navigates away or becomes inactive.
* **Brute-Force & Dictionary Attacks:** Offline attacks against persisted encrypted vault blobs using dictionary lists or GPU crackers.

---

## 2. What Is Protected

1. **At-Rest Confidentiality & Integrity:**
   * All sensitive credential payloads (Banking credentials, passwords, card numbers, CVVs, PINs, notes) are encrypted with **AES-256-GCM** before touching IndexedDB.
   * Authentication tags generated by AES-GCM ensure that any tampering, bit flipping, or corrupt storage entries are detected and rejected upon decryption.
2. **Master Password Privacy:**
   * The master password is never persisted anywhere (not in IndexedDB, `localStorage`, `sessionStorage`, cookies, or logs).
   * The derived master encryption key (`CryptoKey`) is kept only in volatile memory (Angular cryptographic service closure / signals) and is zeroed/dereferenced on vault lock.
3. **UI Obfuscation by Default:**
   * Passwords, Card Numbers, CVVs, and PINs are strictly masked by default across all screens (e.g. `••••••••`, `•••• •••• •••• 1234`).
   * Explicit user interaction (click reveal) with optional automatic timeout masking is required to display plaintext.
4. **Log & Telemetry Cleanliness:**
   * No plaintext credentials, keys, or card details are ever logged to `console.*` or emitted in error events.

---

## 3. What Is Not Protected (Known Browser-Environment Limitations)

1. **Compromised Host / Keyloggers / Malware:**
   * If the host operating system or browser itself has malware, kernel-level keyloggers, or hardware screen capture, inputs can be captured before reaching the Web Crypto APIs.
2. **Active In-Browser DOM / XSS Exploitation:**
   * In a browser environment, any script with full DOM execution rights in the same origin can theoretically intercept keystrokes or hook memory while the vault is in an unlocked state.
3. **Memory Scraping during Unlocked State:**
   * While JavaScript does not provide deterministic manual RAM zeroization for primitive strings (due to Garbage Collection immutable string interning), decrypted payloads are isolated to transient signal state and destroyed upon vault lock.
4. **Operating System Clipboard History:**
   * Third-party clipboard manager utilities on the host OS may retain values copied by the user despite programmatic clipboard clearing attempts.

## 4. Key Derivation Approach

* **Algorithm:** PBKDF2 (Password-Based Key Derivation Function 2) as standardized in RFC 8018 and native to Web Crypto (`PBKDF2` with `SHA-256`).
* **Salt:** Cryptographically secure random 16-byte (128-bit) salt generated via `crypto.getRandomValues(new Uint8Array(16))` per vault.
* **Iterations:** `600,000` iterations (aligned with current OWASP recommendations for PBKDF2-HMAC-SHA256 to provide robust resistance against offline GPU brute-force cracking).
* **Derivation Hierarchy:**
  ```
  Master Password (plaintext input)
        │
        ▼ (PBKDF2-HMAC-SHA256, 600k iterations, 16-byte Salt)
  Master Vault Key (AES-GCM 256-bit CryptoKey, extractable: false)
        │
        ├─► Decrypt / Verify Vault Verification Token (Auth Check)
        └─► Encrypt / Decrypt Individual Vault Items
  ```
* **Vault Auth Verification Token:**
  * To securely verify whether an entered master password is correct *without storing the password or an unencrypted hash*, the vault maintains a `vault_metadata` record containing:
    * `salt` (hex/base64)
    * `iterations` (600,000)
    * `authCheckBlob` (an AES-GCM encrypted known constant string, e.g. `"SECURE_VAULT_AUTH_VALID"`, encrypted with its own unique IV).
  * If AES-GCM decryption of `authCheckBlob` fails (throws `OperationError`), the master password is immediately known to be invalid.

---

## 5. Encryption Approach

* **Algorithm:** **AES-GCM (Galois/Counter Mode)** with 256-bit key length.
* **Initialization Vector (IV / Nonce):**
  * A freshly generated 12-byte (96-bit) cryptographically random IV (`crypto.getRandomValues(new Uint8Array(12))`) is used for **every single encryption operation**.
  * IVs are NEVER reused.
* **Payload Serialization & Packing:**
  * Plaintext JSON objects (`VaultItemPayload`) are encoded into UTF-8 binary buffers via `TextEncoder`.
  * The ciphertext buffer and 12-byte IV are encoded (or stored as typed arrays) in the persistence layer.
* **Authenticated Additional Data (AAD) (Optional Enhancement):**
  * Record IDs or category tags can be bound as AAD to prevent record-swapping attacks.

---

## 6. Local Persistence Approach

* **Storage Engine:** **IndexedDB** using a lightweight, native Promise-based wrapper.
* **Database Schema (`secure_vault_db`):**
  * `vault_meta` store:
    * `key: "config"`
    * `salt`: `Uint8Array`
    * `iterations`: `600000`
    * `authCheckBlob`: `{ iv: Uint8Array, ciphertext: ArrayBuffer }`
    * `createdAt`: timestamp
    * `updatedAt`: timestamp
  * `vault_records` store (KeyPath: `id`):
    * `id`: string (UUID v4)
    * `category`: `'BANKING' | 'CREDIT_CARD' | 'DEBIT_CARD' | 'OTHER'`
    * `title`: string (unencrypted metadata for performant indexed listing / search filtering or selectively encrypted)
    * `subtitle`: string (e.g. masked preview `•••• 1234` or bank name)
    * `encryptedPayload`: `{ iv: Uint8Array, ciphertext: ArrayBuffer }`
    * `createdAt`: timestamp
    * `updatedAt`: timestamp
* **Plaintext Safety Rule:**
  * No sensitive fields (passwords, card numbers, CVVs, PINs, notes) are stored in plaintext in IndexedDB, `localStorage`, or session storage.

---

## 7. Vault Locking & Session Security Approach

* **Memory Lifetime:**
  * Master password strings are wiped immediately after key derivation.
  * The derived `CryptoKey` reference is held solely within an in-memory private signal / service variable.
* **Explicit Lock:**
  * Triggered by user tapping the "Lock Vault" button in the app bar.
  * Immediately clears the `CryptoKey` reference, wipes decrypted item cache, resets UI navigation to `/unlock`, and sets vault state to `LOCKED`.
* **Auto-Lock on Inactivity:**
  * Background inactivity tracker monitors DOM events (`keydown`, `pointerdown`, `touchstart`, `scroll`).
  * If no activity occurs for a configurable timeout (default: 3 minutes), the vault automatically wipes memory keys and locks the UI.
* **Tab Visibility & Lifecycle Locking:**
  * Listening to `document.visibilitychange` (optional configurable setting to auto-lock when switching apps or minimizing the mobile browser).

---

## 8. Clipboard Security

* Sensitive fields copied to the clipboard utilize `navigator.clipboard.writeText(...)`.
* **Zero-Log Guarantee:** The copy action service provides visual toast feedback without emitting secret data to console or error handlers.
* **Auto-Clear Timer:** If supported by the browser, a 30-second timer attempts to clear the clipboard if the copied value still matches.
* **Browser Limitations:** Note that modern mobile OSes (iOS, Android) and browsers restrict background clipboard writes once the tab loses focus, and OS-level clipboard managers may keep independent history.

---

## 9. Summary of Security Invariants
| Property | Implementation |
|---|---|
| Key Derivation | PBKDF2 (SHA-256, 600,000 iterations, 128-bit salt) |
| Encryption | AES-GCM (256-bit, 96-bit unique random IV per record) |
| Integrity | Built-in GCM authentication tag verification |
| Key Storage | Volatile memory only (never written to disk) |
| Plaintext Storage | Strictly Prohibited |
| Password Storage | Zero-Knowledge Auth Check Blob |
| Auto-Lock | Idle timeout + Lock state machine |
